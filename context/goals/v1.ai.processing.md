## Pending edits

- coordinator · context/data-intelligence.md: quarry's `context/layers.md` now settles each boundary of Cerebro's stack (system tools → quarry → go-ai → Cerebro) as signatures and schemas traced to this note's design tasks or spike evidence. The tool contracts move to schema "2", JSON Lines with Markdown inside as the text layer and structured text with no consumer cut by measurement over ~/docs, and grow by addition only from there. quarry's library exports `infer` (vision, transcription, embedding, and chunker interfaces free of go-ai, a cache, and a pipeline that yields inference texts, batches, and done as made) and `job` (one job's dispatch and inference, cancelled by its own context, yielding its updates). quarry has no events package, emits no CloudEvents itself, and declares no event kinds, so it has no `messaging.go`: each package that produces a change holds its JSON shapes in its ordinary files, beside its other types (dispatch's parts, outputs, and warnings; infer's inference texts, batches, chunks, done, and profile; job's `Update` and checkpoint, version "1"). quarry's nested module `model` holds the one go-ai adapter to `infer`'s interfaces, which Cerebro and quarry's `cmd/docinfer` both import; Cerebro only wires it. Cerebro starts from Go Elemental Commands (Submit, OpenUpload, AppendChunk, CompleteUpload, AbortUpload, CancelJob) and Queries (GetJob, GetUpload, ListProfiles); JetStream streams CEREBRO_WORK, CEREBRO_JOBS, and CEREBRO_UPLOADS beside an object store, each job's events on one subject of its own, `cerebro.job.<job>`, for the job's gap-free sequence, which supersedes this note's "one event stream per job": one shared CEREBRO_JOBS stream, a subject per job (messaging.md's subject and stream conventions govern a web service's events for committed command mutations, not a job's progress and result stream); CloudEvents 1.0 events in binary mode on NATS headers, whose `cerebro.job.*` types Cerebro defines in its own `messaging.go` with `event.Define` over quarry's `job.Update` or its own data types, which sit beside its other types; and a `completed` event whose manifest carries the resolved profile, the job's contiguous sequence range, batch and chunk counts, a digest, and quarry's counts. The open items pass to `protocol` (live sources, the small-document size), `events` (the batch cap, large inference texts), `state` (stream and bucket names), `chunks` (storing chunks by identity), `metadata` (typed metadata shapes), `athena-mapping` (typed cells for `sparse_rows`), `text-layer` (`ocr_text`'s return), and v1.ai.client (transcription retry).
- coordinator · context/messaging.md: scope the subject and stream conventions (an event's NATS subject is its type; one owner's stream captures `<prefix>.>`) to a web service's events for committed mutations of executed commands. A job's progress and result stream, such as Cerebro's (`cerebro.job.<job>`, one subject per job for the job's gap-free sequence), is a different use case those conventions don't govern.
- architecture · standards/go-elemental/principles/topology-and-naming.md (architecture task): a package's events live with the package that produces the change: its event kinds sit in that package's `messaging.go`, and their data types beside its other types, as go-web-service's `domain/organization/messaging.go` and `domain/document/messaging.go` hold only their `event.Define[T]` calls over data types in the package's `entities.go` (`OrganizationData`, `LogoUploadedData`; `DirectoryData`, `FileUploadedData`), and `admin/database/messaging.go` defines its events over `string`.
