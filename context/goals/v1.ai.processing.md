## Task brief · v1.ai.processing · mail-hardening

**Problem**

Acceptance left four follow-ups for docproc-mail, and tasks.final reruns against the release this
task cuts. Schema "2" made v0.1.2 about twice as slow on plaso's store (3.34 s against the spike's
1.61 s), and 1.27 times as slow on scale.mboxrd. Nobody has yet broken down where a message's read
spends that time. The RTF text reader runs a table's cells together. A Microsoft Exchange (MAPI)
message that is encrypted, signed, or rights-managed in a .msg or .pst gets no warning that its
content wasn't read, and the text of a clear-signed one is never read. No golden pins the five
Markdown changes that v0.1.2's CHANGELOG lists. Under the architect's standing rules, known
breakage is fixed before the tag, trailing dependencies are taken, and found improvements land
here.

**Behaviors**

1. Every committed golden stays byte-identical through the performance work. A new fixture
   message and its golden pin each Markdown change v0.1.2 lists:
   - a math span written as `$…$` or `$$…$$`
   - link text that keeps its edge whitespace, with a line ending written as `&#10;`
   - a link's or an image's title written whole
   - an `<img>` without a `src` left out
   - a leading `+`, `1)`, or autolink-like `<` escaped
2. docproc's docs break down where a schema "2" message's read spends its time, stage by stage:
   - body selection and decoding
   - HTML to Markdown through htmd, with its `bare` pass
   - the image-source rewrite
   - the content rule's sentence split and alignment
   - escaping
   - the JSON line and the media

   The breakdown comes from samply profiles of the musl release binary on plaso's store and
   scale.mboxrd, taken before and after the fixes. It names each waste found: a redundant pass, a
   needless allocation or copy, or work done for output that is never written. It also says how
   each was removed. No time target is set.
3. Each waste the breakdown names is removed, and the output stays byte-identical, goldens
   included.
4. In the RTF text reader:
   - `\cell` and `\nestcell` are each read as a tab, so a row's cells read as one line, separated
     by single spaces.
   - `\row`, `\page`, and `\sect` are each read as a line break.
   - The `\nonesttables` fallback group is skipped, so a nested table's text is read once.
5. A .msg or .pst message whose class is `IPM.Note.SMIME`, or ends in `.SMIME` (compared without
   regard to case), gets the warning an opaque S/MIME MIME part gets, whatever its attachments.
6. A clear-signed .msg or .pst message, class `IPM.Note.SMIME.MultipartSigned`, has its one
   `multipart/signed` attachment read the way an .eml's signed content is read. When the message
   stores no body of its own, its Markdown is made from that content's bodies. The attachment
   itself stays listed as stored.
7. A rights-managed message gets a warning that its content isn't read, in every format. Its sign
   is an attachment named `message.rpmsg`, or, in MIME, a `Content-Class: rpmsg.message` header.
8. The tool README's Limits and docproc's limits document state behaviors 5 to 7 as they now are.
   The allocator statements stay as they are. docproc-mail's CHANGELOG records each change in its
   `v0.1.4` section, and `--version` prints `0.1.4`.

## Decisions

- design: held MimeKit at 4.18.2 in mail's fixture generator: MsgKit 3.0.6 and PstBuilder.Eml 1.3.0, their latest, are built on MimeKit 4, so 5.0.0 is declined until one releases on 5 (reaffirmed at reports' plan).
- plan: held typed-path at 0.12.4: onenote_parser 2.1.0, its latest, requires ^0.12.3, so 0.13.0 is declined and moves only with onenote_parser (reaffirmed at reports' plan).
- onenote, reports, acceptance: the architect's standing rules for this goal's tasks: a known behavior that breaks functionality is fixed before the tag, with a patch release of what already shipped it ("we shouldn't ship known behaviors that break functionality"); what currency reports trailing is taken, not held, unless a dependency forces it ("the whole point of currency is to avoid incurring technical debt"); and a found improvement lands in its task rather than backlog ("we want to make sure the delivered goal is in the most optimal state we can place it in") — rejected: tagging with a backlog entry.
- acceptance (plan): the office, mail, and OneNote benches rerun from scratch copies of their spikes against the release binaries, only the CLI call changed and schema "2" read; no bench is committed — rejected: porting the benches into docproc.

- mail-hardening (plan): kept musl's allocator for docproc-mail. Rejected: mimalloc 0.1.52.
  Measured, it was 13 to 35% faster with about twice the peak memory, but its C build needs zig or
  a musl C toolchain ("zero reason to pull in zig toolchain").
- mail-hardening (plan): performance work for this goal's tasks is held to no metric bar. A
  slowdown is broken down stage by stage, each stage's waste is removed with the output
  byte-identical, and the reasoning goes in the docs ("ensure that the functionality we are aiming
  for is effectively deconstructed and performs optimally"). Rejected: the spike's time within 12%.
- mail-hardening (plan): a profiler is fetched for the session through `mise x` (samply), and is
  never pinned or committed.
- mail-hardening (plan): docproc-onenote's hashbrown 0.17.2 waits under its Unreleased section,
  with no release, so tasks.final reruns against `tools/onenote/v0.1.1`.
